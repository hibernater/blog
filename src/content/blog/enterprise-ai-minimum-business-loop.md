讨论企业 AI 架构，很容易画出一张什么都有的图：Ontology、Knowledge、Planning、Workflow、Agent Runtime、Prediction、Optimization、Simulation、Eval、Learning、Governance……

这些能力并非不重要。问题在于，如果把完整架构直接当成第一期建设清单，团队通常会遇到两种结果：

- 平台做了很久，真实业务还没有跑起来；
- 为了让所有模块看起来都有用，反过来给技术寻找场景。

我更认可另一条路径：**完整架构用来防止长期漏项，第一期则只跑一条业务最小闭环。**

最小闭环不是功能最少，也不是做一个聊天 Demo。它的判断标准是：

> 用最少的技术组件，完成一次真实的“状态识别—行动—状态改变—结果回写”。

## 最小闭环与最小功能不是一回事

一个系统能生成报告、话术或建议，不代表它已经形成业务闭环。

例如：

```text
读取客户资料
→ 生成一份跟进建议
→ 人工复制到另一个系统
```

这可能是有价值的 Copilot，但系统并不知道建议有没有执行，也不知道执行后客户状态有没有变化，更无法判断下一轮应该改什么。

一个最小业务闭环至少是：

```text
真实业务事件触发
→ 识别业务对象当前状态
→ 生成一个明确可执行的动作
→ 动作通过工具、工作流或人真实发生
→ 结果改变业务状态并被记录
→ 运行轨迹进入复盘与改进
```

这里每一环都不能少。少了事件，系统只能等人提问；少了状态，判断没有可靠依据；少了动作，系统只是分析工具；少了执行，建议没有落地；少了结果回写，系统永远不知道自己做得好不好。

## 先选“闭环”，不要先选“技术栈”

第一期最重要的产物不是平台选型表，而是一张业务实施卡：

```text
场景名称：
业务目标：
核心业务对象：
触发事件：
当前状态来源：
可执行动作：
执行系统与责任人：
第一期最简决策机制：
第一期结果信号：
权限、审批与回退边界：
验收指标：
明确暂不建设的模块：
```

这张卡会迫使团队先回答真实问题。

例如，“提升销售效率”太宽，不是一个可运行场景；“高意向客户 24 小时未跟进时，生成下一步动作并进入销售待办，执行后回写联系结果”才接近闭环。

同样，“优化供应链”不是闭环；“订单承诺日期出现风险时，识别原因、生成候选干预动作、由负责人审批执行，并记录交期是否恢复”才是。

技术应该在这些问题明确之后出现，而不是之前。

## 第一阶段只需要证明六件事

一条企业 AI 场景能否成立，可以先用六个验收问题判断。

### 1. 真实事件能否触发一次运行

不是用户临时复制一段文字来问，而是订单变化、客户沉默、库存异常、工单升级等真实事件能进入系统。

### 2. 系统能否识别对象当前状态

它知道处理的是哪个客户、订单、合同或工单，能够读取当前有效状态，而不是只根据一段脱离上下文的文字猜测。

### 3. 系统能否输出明确动作

输出应该是可执行动作，例如创建待办、补充材料、发起审批、更新承诺、调整优先级，而不只是“建议进一步关注”。

### 4. 动作能否真实发生

动作通过 API、工作流、业务工具或明确责任人被执行。高风险动作可以要求审批，但不能永远停在报告里。

### 5. 结果能否回写业务状态

系统知道动作是否执行、对象状态是否变化、目标是否改善。最终结果暂时不可见时，也要记录可观测的中间状态。

### 6. 运行证据能否形成受审核的改进

Trace 应能支持复盘：是知识错了、规则错了、状态缺失、工具失败，还是审批边界不合理？改进以版本化 Patch 进入评测和发布，而不是让一条反馈直接改坏生产系统。

如果只能生成建议、报告或话术，不能验证真实状态变化，就还不是业务最小闭环。

## 最简不等于一律使用 LLM

不同场景的第一期，最简技术组合并不相同。

### 状态稳定、分支可枚举

优先使用规则、状态机和工作流。LLM 可以处理非结构化输入，但不必主控整个流程。

### 输入复杂，但业务路径固定

让 LLM 负责抽取、分类或生成结构化候选，再交给确定性工作流执行和校验。

### 知识密集、规则频繁变化

先建设带来源、版本、权限和有效期的知识层，而不是先做模型微调。

### 开放问题、候选动作难枚举

可以引入 LLM Planner 生成候选计划，但动作目录、权限、退出条件和验收标准必须明确。

### 多对象争夺有限资源

这不是“让 LLM 排个序”能解决的问题。需要目标函数、约束和运筹优化；但只有当资源竞争真实出现时才值得建设。

最小架构的原则不是“所有场景都用同一套轻技术”，而是：**每种业务问题只引入恰好能够解决它的机制。**

## 什么时候应该升级架构

第一条闭环跑起来后，新增模块应由真实复杂度触发。

| 运行中出现的问题 | 应增加的机制 | 不应误加的东西 |
|---|---|---|
| 状态说不清、对象对不上 | 对象 / 状态 / 事件模型 | 先上复杂规划器 |
| 未来结果有概率差异 | 预测模型 | 把人工规则包装成“AI 评分” |
| 高概率对象未必值得干预 | 因果 / Uplift 与实验 | 只按成功率排序 |
| 多对象争夺人、库存、预算 | 运筹与优化 | 让 LLM 自由分配 |
| 多步行动有长期连锁影响 | 搜索、仿真、滚动规划 | 用合成结果替代真实结果 |
| 例外无法预先枚举 | 动态事项与异常 Agent | 推翻稳定的确定性主干 |
| 反馈延迟、稀疏、难归因 | 状态轨迹、分层信号、真实实验 | 直接制造合成 ROI |
| 规则、知识、模型频繁变化 | 版本、评测、灰度、回滚 | 反馈直接修改生产系统 |

这张表背后的判断很简单：

> 每增加一个复杂模块，都必须对应一个已经真实出现的业务复杂度。

不是因为某个技术流行，也不是因为完整架构图上有它。

## 三个接口应该从第一天稳定

组件可以逐步增加，但有三个接口最好从第一条闭环就保持清楚。

### Action Plan：系统准备做什么

动作、前置条件、执行者、工具、审批要求和完成标准应被结构化表达。这样即使未来从规则升级为 Planner，执行层也不必推倒重来。

### State Transition + Trace：世界发生了什么变化

每次运行都要记录前置状态、采取的动作、执行结果和新状态。没有这条轨迹，评测、归因和审计都无从谈起。

### Versioned PatchSet：系统准备改什么

复盘产生的知识、规则、流程或策略修改，应形成可审核、可评测、可发布、可回滚的版本，而不是直接覆盖生产能力。

稳定的是这三个业务接口，不是第一期选中的某个 Agent 框架。

## 四个常见反例

### 反例一：先建全企业 Ontology

单一场景、对象少、字段稳定时，清晰的数据结构、主键和状态定义就可能够用。只有跨系统语义冲突和对象关系复杂度真正出现，才逐步升级。

### 反例二：让 LLM 主控所有流程

确定性主干交给规则和工作流，LLM 放在语义理解、候选生成和长尾异常等开放节点，通常更可靠。

### 反例三：把人工审批当成闭环失败

第一期让 AI 做、人审批，并不丢人。只要审批节点明确、上下文完整、结果可回写，它就是受治理的 G2 闭环，也是未来放权的证据来源。

### 反例四：一开始就追求跨部门大闭环

闭环越大，状态来源、责任边界、系统依赖和反馈周期越难控制。先在一个业务对象、一个明确事件和一组有限动作上闭合，再复制和连接。

## 从最小闭环走向规模化

一条可持续的演进路径通常是：

```text
单对象、单流程、人工确认
→ 对象与状态标准化，运行轨迹完整
→ 风险和结果可预测，异常提前发现
→ 多对象、多资源下进行排序和优化
→ 实验、归因和版本化学习
→ 多步规划、滚动决策与有限仿真
```

这不是必须逐级打怪的路线图。一个简单流程可以长期停在第二步稳定运行；一个供应链场景也可能很快遇到资源优化问题。关键不是走到第几层，而是每次升级都有业务证据。

## 最终判断

完整架构和场景最小闭环并不矛盾：

```text
完整架构负责：不遗漏长期能力与演进方向
场景架构负责：在当前复杂度下只建设真正需要的部分
企业实例负责：把对象、动作、系统、责任人和结果接进真实业务
```

企业 AI 第一阶段最该证明的，不是模型多聪明、平台多完整，而是：

> 一个真实业务事件，能否触发系统理解状态，推动一个受治理的动作，改变业务世界，并把结果带回下一轮。

先把这一圈跑起来。剩下的技术，应该由真实复杂度来召唤。
