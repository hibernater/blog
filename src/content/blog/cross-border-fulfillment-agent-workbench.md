> 说明：本文是上一篇《一家跨境供应链公司如何选择第一条 AI 业务闭环》的下篇。上篇讲怎么选场景，本篇讲选定履约时效之后，系统应该怎么设计。文中架构处于设计与分阶段建设中，不是已全部上线的系统。

选定"履约时效确定性"作为北极星之后，下一个决策是产品形态。

最容易做的选择是聊天入口：给业务团队一个对话框，想查什么问 AI。这个形态几乎注定失败——跟单员每天要盯几百个订单的状态，不可能一个个"问"出来；老板要的是风险总览，不是问答记录。

正确的形态是：

> **围绕一条核心业务链路的 Agent 工作台——业务人员操作订单、异常、确认和复盘；系统底层调用 Agent、工具和模型。**

一句话原则：**业务人员操作 Run，不操作 Agent。**他们不应该面对 prompt、model config、context window；他们应该面对今日风险订单、待我确认、履约监控、复盘与规则。

## 一、为什么跟单业务是 Agent 工作台的合适载体

跨境跟单有几个天然适配 Agent 系统的特征：

1. **高频重复**：每天都有订单在各节点流转，样本量足够；
2. **状态天然结构化**：供应商确认、发货、入库、揽收、清关、派送，节点可枚举；
3. **信息极度分散**：物流商后台、Excel、邮件、微信群——这正是人工最痛、AI 采集整合价值最大的地方；
4. **动作边界清楚**：整理表格、标记异常、生成通知是低风险动作；通知大客户、切换物流商、赔付评估是高风险动作，分级明确；
5. **结果快速可测**：时效以天计，异常处理效果几天内可见。

## 二、业务对象与事件：系统的地基

没有业务对象层，AI 只能总结文字，不能稳定跑业务——它不知道自己在操作什么，也无法把今天的异常和明天的规则连起来。

T 公司的核心业务对象至少包括：

```text
订单 / 包裹 / SKU
供应商 / 物流商 / 物流线路
客户 / 业务接口人
异常类型
内部时效目标（Shadow SLA）
责任边界
```

对象之上是状态和指标：

```text
状态：订单节点状态、供应商响应状态、物流节点状态、异常状态
指标：ETA、P50/P90/P95 时效、节点停留时长、超时风险、
     异常率、提前预警时间、动作采纳率、动作有效率
```

其中最关键的机制是 **SLA 时钟**：每个订单在每个节点都有时间预算，时钟走到阈值就触发事件——"供应商 48 小时未确认"、"物流 72 小时未更新"、"ETA 预计超时"。事件驱动 Agent 运行，而不是等人来问。

## 三、跟单闭环：一条完整的 Run

系统的基本运行单位不是"对话"，而是有运行合同的业务 Run。以跟单 Run 为例：

```text
拉取状态 → 标准化节点 → 判断风险 → 动作分流 → 审批/执行 → 复盘回写
```

每一步展开：

1. **拉取状态**：从物流商后台、表格、邮件、后台系统采集原始信息；
2. **标准化节点**：把杂乱信息转成统一状态机（供应商未确认 / 未发货 / 未入库 / 未揽收 / 长时间未更新 / 清关异常 / 派送失败）；
3. **判断风险**：订单卡在哪个节点、停留多久、是否超节点预算、ETA 是否会超时、原因是什么、责任方是谁；
4. **动作分流**：低风险动作自动执行（整理表格、标记异常、生成通知草稿）；高风险动作进入审批；
5. **审批/执行**：审批结果留痕，由执行层落地；
6. **复盘回写**：运行结论沉淀为规则，下次 Run 自动加载。

每个 Run 都要有明确的运行合同：目标、输入、边界、步骤、输出、验收标准、留痕方式、升级条件。**Agent 不是闭环，Harness 才是闭环。**

## 四、动作分级：人机分工的核心机制

工作台的信任基础是动作分级：

| 等级 | 动作类型 | 示例 |
|---|---|---|
| L0 | 只读 | 查询订单、查看物流 |
| L1 | 建议 | 提示异常、给出原因 |
| L2 | 草稿 | 生成通知、表格、方案 |
| L3 | 审批后执行 | 通知客户、换供应商、换物流、赔付评估 |
| L4 | 自动执行 | 低风险重复动作 |

必须进入审批的动作清单要显式定义：通知大客户、切换高成本物流、更换核心供应商、赔付评估、对外 SLA 承诺、退款补发。

治理不是事后检查，而是**动作前的闸门**：不是所有 AI 动作都自动执行；高风险动作必须审批；所有动作必须留痕；可撤销动作必须保留回滚路径。

人的角色也随之清晰：老板看 SLA、风险订单和经营复盘；跟单和业务员处理异常、补充事实、确认动作。他们通过确认、驳回、补事实和复盘来"训练"系统——这是组织参与 AI 建设最自然的方式。

## 五、结果回写：系统变聪明的机制

每次 Run 结束都要回答一个问题：**这次系统多知道了什么？**

答案沉淀为五类版本化 Patch：

| Patch 类型 | 含义 | 示例 |
|---|---|---|
| Ontology Patch | 对象/状态修正 | 新增异常类型、新增物流节点 |
| Knowledge Patch | 业务规律 | 某线路 P90 时效从 12 天变 18 天 |
| Workflow Patch | 流程调整 | 某类订单提前 48 小时预警 |
| Metric Patch | 指标口径 | 调整 ETA 风险阈值 |
| Governance Patch | 权限/审批规则 | 高价值客户通知必须审批 |

这些 Patch 进入业务 Skill 网络，下次 Run 自动加载。没有这个机制，工作台只是自动化工具；有了它，每一单、每一次异常、每一次人工纠正都在让系统变强——这是企业 AI 化的复利来源。

## 六、从单条闭环到 Business OS 的升级路径

工作台不是终点，它是 Business OS 的第一块。升级分三个阶段：

### 阶段一：履约可观测（当前建设中）

所有订单状态统一、异常可见、人工少整理表。核心能力：状态统一、节点标准化、异常识别、通知草稿、待确认队列、每周复盘。

### 阶段二：履约可预测、可干预

从"异常发生后 AI 帮人整理"升级为"异常发生前 AI 提前预警"：ETA 预测、节点时间预算、物流商和供应商评分、高风险订单雷达、切换建议、动作效果复盘。AI 的价值从"省人"变成"减少损失"。

### 阶段三：履约可承诺

把供应链能力产品化。关键纪律是**先跑内部 Shadow SLA，不要直接对客户承诺"晚就赔"**：

```text
可观测 → 可预测 → 可干预 → 可复盘
→ 内部 Shadow SLA → 小范围客户 SLA → 时效保障产品化
```

到阶段三，系统开始面对多目标权衡——为了更快是否接受更高物流成本、为了体验是否提前赔付——这时单条链路的工作台才真正长成经营层面的 Business OS。

## 七、技术判断：买现成的引擎，自建业务层

最后一个关键决策：**Agent 能力买现成的，业务流和 Harness 必须自己长出来。**

成熟的 Agent 引擎（长期协同类、工程执行类）应该直接复用，公司不应该自研通用 Agent 框架，也不应该把这些工具的原生界面直接给业务人员。真正需要自建的是四层：

```text
业务对象层：订单、供应商、线路、异常的语义模型
Workflow / Harness 层：每条链路的运行合同
动作与连接层：对接后台、物流商 API、通知渠道
反馈学习层：Patch 沉淀与版本管理
```

这四层是别人拿不走的壁垒——引擎会不断更新换代，但业务对象、运行合同和沉淀下来的 Skill 网络属于公司自己。

## 结语

跨境履约 Agent 工作台的设计可以压缩成四句话：

> **对象和事件是地基，SLA 时钟驱动运行，动作分级建立信任，结果回写形成复利。**
