讨论长程 Agent，最容易被接受的叙事是：上下文窗口越来越长，模型记得越来越多，所以 Agent 能执行的任务越来越长。

这个叙事把两个不同的问题混在了一起。

上下文长度解决的是**一次推理能看到多少信息**。而一个跨三天的履约任务真正的难点是：第二天凌晨进程重启了怎么办？供应商七小时后才回复怎么办？审批人周末不上线怎么办？同一个动作因为重试被执行了两次怎么办？

我的判断是：

> **长程 Agent 的可靠性，首先是持久执行、状态分层、外部核验和故障恢复的工程问题；上下文长度只是其中一个输入条件，而且往往不是瓶颈。**

## 一、“上下文够长就可靠”错在哪里

一个跨天任务的生命周期里，会发生很多与推理无关的事情：

- 进程重启、部署更新、机器迁移；
- 外部系统超时、限流、返回不一致数据;
- 人工审批挂起数小时到数天；
- 同一事件重复投递，同一动作被触发两次；
- 任务执行到一半，依赖的业务对象状态被别人改了。

这些问题没有一个能靠“记住更多上下文”解决。相反，把整个任务历史塞进上下文重新推理，还会引入新问题：每次恢复都可能做出与上次不一致的判断，任务行为变得不可复现。

长上下文让 Agent **更聪明**，但不会让它**更可靠**。可靠性来自另一套机制。

## 二、先把四种状态拆开

长程任务失控的第一原因，通常是把所有状态混在一个会话里。至少要拆开四层：

```text
对话状态：用户和 Agent 说过什么、当前意图是什么
任务状态：这个任务执行到哪一步、在等什么、谁负责
业务状态：订单、合同、库存在业务系统里的真实状态
版本状态：当时用的是哪个版本的 Prompt、Skill、Workflow 和权限
```

四层状态的事实源不同、生命周期不同、恢复要求也不同：

- 对话状态丢了，最多重新问一次；
- 任务状态丢了，跨天任务就变成孤儿；
- 业务状态从来不该存在 Agent 侧——它的事实源永远是业务系统；
- 版本状态丢了，事后既无法复现问题，也无法回答“当时为什么这么做”。

判断一个长程 Agent 系统是否成熟，可以直接问：**重启之后，它恢复的是哪一层状态？** 只能恢复对话的系统，还停留在聊天助手阶段。

## 三、持久执行的六个机制

跨天任务需要的核心机制，工作流领域已经积累了几十年，值得直接借用而不是重新发明：

### Event History：把执行过程记成事实

每一步决策、每一次工具调用、每一个外部响应都作为事件追加记录。恢复时不是“重新想一遍”，而是从事件历史确定性地重建到中断位置。

### Checkpoint：明确的可恢复点

不是每个 Token 都要可恢复，但每个关键状态转换后必须落盘。恢复粒度是设计决策：太粗则重复执行太多，太细则成本高昂。

### Wait / Signal：等待是常态，不是异常

供应商回复、人工审批、定时触发都是长程任务的正常组成。系统必须能挂起数小时到数天而不占用资源，被外部信号唤醒后从正确位置继续。

### Retry：区分可重试与不可重试

网络超时可以重试；“余额不足”重试一百次也没用。重试策略必须按失败类型区分，且有上限和退避，不能把重试当成万能修复。

### Idempotency：同一动作执行两次等于执行一次

事件重复投递和重试都会导致动作被触发多次。发通知重复一次是打扰，扣款重复一次是事故。所有有副作用的动作都需要幂等键。

### Compensation：撤不回的动作要能补偿

跨系统的长任务无法用数据库事务包住。已经执行的动作如果后续步骤失败，需要明确的补偿动作——取消预订、冲正记录、发送更正——而不是假装能回滚。

## 四、模型说“完成”不算完成

长程任务还有一个特有的陷阱：**把模型的自我报告当成事实**。

Tool 返回 success、Agent 说“已处理完毕”、Workflow 走到终点节点，这三件事都不等于业务状态真的发生了预期变化。API 可能返回成功但下游异步失败；模型可能理解错了返回结构；动作可能改对了状态但改错了对象。

因此关键动作之后必须**回读业务事实源**：订单状态真的变了吗？变化的是预期的那个对象吗？核对不一致时，进入重试、补偿或人工升级，而不是继续往下走。

这也决定了长程系统的评测不能只看最终答案。至少要分层看：

```text
系统层：崩溃率、恢复成功率、挂起任务堆积
动作层：执行正确率、幂等违规、补偿触发率
轨迹层：步骤合理性、重复劳动、无效循环
业务层：SLA 达成、结果指标、护栏指标
治理层：越权尝试、审批绕过、审计完整性
经济层：单任务成本、人工接管率
```

一个在业务层看起来达标的系统，可能在动作层积累着大量靠人工兜底掩盖的问题。

## 五、人审和版本迁移：最容易被忽略的两个长程问题

### 人是长程任务的一等参与者

跨天任务几乎必然包含人工节点：审批、补充信息、处理例外。设计时要回答的不是“要不要人审”，而是：

- 审批请求带不带足够上下文，让人五分钟内能判断；
- 审批人超时不响应，升级给谁；
- 人工修改了中间结果，Agent 后续步骤如何感知；
- 人工直接在业务系统里操作了，任务状态如何对账。

把人当成“异常情况”的长程系统，会在每一次正常的人工介入中积累状态漂移。

### 任务比版本活得长

一个跑三周的任务，中途系统可能发布了两个新版本。新版本的 Prompt、Skill 或审批边界变了，进行中的任务怎么办？

至少要有明确决策：存量任务锁定旧版本跑完，还是在安全的 Checkpoint 上迁移到新版本。没有版本状态记录的系统，连这个问题都无法提出——这也是前面强调版本状态的原因。

## 六、结语

长上下文是真实的进步，它让 Agent 在单次推理里能处理更复杂的信息。但把长程可靠性寄望于上下文长度，等于把工程问题当成了模型问题。

一个值得信任的长程 Agent 系统，特征不是“它能记住三天前的对话”，而是：

> **任何时刻杀掉进程，它都能从事件历史恢复到正确位置；任何动作重复触发，业务状态都不会被破坏；任何模型宣称的完成，都经过了业务事实源的核验。**

这些能力和模型无关，和纪律有关。
