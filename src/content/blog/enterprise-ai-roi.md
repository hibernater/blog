企业做 AI 项目，最常见的 ROI 算法是：

```text
每人每天节省 1 小时
× 使用人数
× 人力单价
= AI 创造的价值
```

这个数字很容易做大，也很容易错。

员工节省的一小时未必转化成更高产出；任务可能只是从执行者转移给审核者；模型成本很低，但集成、数据、人工兜底和异常处理很贵；最终业务指标变好，也未必由 AI 导致。

另一些团队则用调用量、活跃用户、答案准确率或 Demo 完成率证明价值。这些可以说明系统被使用、某个能力可用，却不能证明企业因此获得了增量收益。

我更认可的判断是：

> **企业 AI 的 ROI，不是模型效率指标，而是一份带基线、护栏、全成本、结果窗口和归因口径的 Result Contract。**

## 一、先排除四种“看起来很像 ROI”的指标

### 1. 节省工时

节省工时只有在至少一种结果发生时才转化为价值：

- 同样人数完成更多业务；
- 减少加班、外包或新增招聘；
- 缩短交付周期并改善收入或客户体验；
- 员工把时间转向了可验证的高价值工作。

如果只是“用户觉得快了”，但组织产出、成本和周期没有变化，工时只能算过程指标。

### 2. 调用量、Token 和活跃用户

这些指标说明采用程度和资源消耗，不说明业务收益。调用越多甚至可能意味着流程更绕、重复重试更多、单位任务成本更高。

### 3. 模型准确率

离线准确率可以证明某个能力达标，却不自动等于端到端结果。识别准确，但动作没有执行；动作执行了，但改变了错误对象；局部判断正确，但伤害了护栏指标，项目仍可能没有价值。

### 4. 模型或项目组自报“任务完成”

Agent 说“已完成”、Tool 返回 success、Workflow 走到终点，都不能替代真实状态核验。只有业务事实源确认订单、客户、库存、合同或工单发生了预期变化，才算完成了对应动作。

## 二、先定义 Result Contract，再谈 ROI

每个 AI 项目在启动前，都应该把结果写成一份可审查的契约，而不是只写“提升效率”或“促进增长”。

一份最小 Result Contract 至少包括：

```text
业务目标
+ 目标对象和当前基线
+ 主结果指标
+ 过程 / 领先指标
+ 护栏指标
+ 结果观察窗口
+ 责任人
+ 成本与资源预算
+ 风险边界
+ 证据与归因口径
+ 扩量、维持、停止条件
```

例如销售 Agent 不能只写“提高收入”，还要约束退款、投诉、触达频次、客户透支和长期留存；履约 Agent 不能只优化准时率，还要看加急成本、供应商关系、错误承诺和人工干预。

这里最重要的是把四类价值分开：

1. **收入增量**：更多成交、更高客单、更高续费；
2. **成本节省**：减少人工、外包、返工、库存或异常处置；
3. **风险损失降低**：降低赔付、违约、欺诈、合规和事故的期望损失；
4. **时效与资本价值**：缩短回款、交付、库存周转或决策周期带来的价值。

四类价值不能随意相加。同一次交付提速既算了工时节省，又把全部收入增长归给提速，就可能重复计算。

## 三、ROI 必须使用全口径成本

企业 AI 项目的完整成本不只是 Token。

至少要计算：

### 一次性建设成本

- 数据清理与接入；
- 系统集成和连接器；
- Ontology、指标和 Action 定义；
- Workflow、Harness 和权限配置；
- Eval 集、Shadow 和上线验证；
- 培训、流程调整和组织切换。

### 持续运行成本

- 模型和 Token；
- Tool、搜索、存储与算力；
- 人工审核和例外处理；
- 失败重试、赔付与补偿；
- 数据、知识、Prompt、Skill 和 Workflow 维护；
- 安全、审计、监控和版本发布；
- 供应商费用与内部平台分摊。

### 机会成本

- 业务专家被项目占用的时间；
- 新旧流程双轨运行的成本；
- 错误自动化导致的返工与信任损失；
- 选择这个项目而放弃其他项目的资源成本。

因此，一个基础公式可以写成：

```text
增量收益
= 收入增量
+ 可兑现的成本节省
+ 风险期望损失降低
+ 可计量的时效 / 资本价值

全口径成本
= 一次性建设成本摊销
+ 持续技术成本
+ 人工监督与异常成本
+ 治理合规成本
+ 失败与机会成本

ROI
=（经归因的增量收益 - 全口径成本）/ 全口径成本
```

这里“经归因”三个字，比公式本身更重要。

## 四、业务结果变好，不等于 AI 创造了增量

最终业务指标常常受到市场变化、促销、季节、人员调整和客户结构影响。AI 上线后指标变好，只能说明相关，不能自动说明因果。

可以按场景选择不同强度的归因方式：

### 离线 Replay

用历史任务回放，比较新旧策略在同一批样本上的表现。适合上线前筛选方案，但无法完全模拟真实执行和环境反应。

### Shadow Mode

AI 生成建议但不执行，与人工真实动作和结果比较。它能评估覆盖率、建议质量和潜在风险，但不能证明组织采用后的最终效果。

### A/B 或随机实验

在可随机分组的场景中，对相似对象使用不同策略，直接估计增量。它通常最有说服力，但要防止组间干扰、执行不一致和观察窗口过短。

### 准实验

无法随机时，可以使用分阶段上线、匹配、差分中的差分、断点等方法，尽量构造可信反事实。前提是明确假设和偏差，不能把复杂统计方法当成“自动因果”。

### 分群与长期观察

平均效果可能掩盖差异。AI 可能只对某类客户、某个风险段或某种异常有效，也可能短期改善、长期反噬。应同时检查分群、护栏和持续性。

对于外部随机性强的结果，系统更适合承诺：

> 在明确约束和结果窗口内，提高目标达成概率，并用实验或可信归因估计真实增量。

而不是承诺“保证 GMV”或“保证客户回复”。

## 五、一个可复算的示意例子

下面是一个**纯示意、非真实项目数据**的履约异常处理案例。

某团队每月处理一批订单异常。AI 工作台上线后，经过对照和状态核验，观察到：

- 人工处理时间减少 45 小时，按 120 元/小时计，可兑现价值为 5,400 元；
- 加急、赔付和延期处置成本减少 4,320 元；
- 当月经归因的增量收益合计 9,720 元。

如果只计算模型与平台费用：

| 成本项 | 月成本 |
|---|---:|
| 模型与工具 | 1,800 元 |
| 平台运行 | 1,500 元 |
| 表面可见成本 | 3,300 元 |

那么表面 ROI 是：

```text
(9,720 - 3,300) / 3,300 = 194.5%
```

看起来非常漂亮。

但把遗漏成本补齐：

| 成本项 | 月成本 |
|---|---:|
| 模型与工具 | 1,800 元 |
| 平台运行 | 1,500 元 |
| 人工审核与异常处理 | 2,400 元 |
| 数据集成和建设成本月度摊销 | 3,000 元 |
| 全口径成本 | 8,700 元 |

真实口径下：

```text
(9,720 - 8,700) / 8,700 = 11.7%
```

项目仍然为正，但远没有“Token 很便宜，所以毛利很高”那么乐观。

这个结果也不能直接得出“立即全量推广”。团队还要问：

- 11.7% 是否高于资本和项目机会成本；
- 扩量后人工审核比例会下降还是上升；
- 新场景能否复用连接器、Ontology、Workflow 和 Eval；
- 减少的处理时间是否真的兑现，而不是转移到别处；
- 护栏指标和长期客户结果是否稳定。

## 六、用门槛管理项目，而不是用故事争论

一项企业 AI 投资最好设置四类 Gate。

### Pilot Gate：值得进入真实试点吗

检查基线、目标、状态、动作、结果信号和风险边界是否可定义。不能观测结果、不能执行动作的项目，先不要计算宏大 ROI。

### Production Gate：值得进入生产吗

检查系统可靠性、动作正确性、状态对账、权限、护栏、人工接管和故障恢复。业务指标偶然变好，不足以让不可靠系统进入生产。

### Scale Gate：值得扩量吗

检查经归因的增量收益、全口径成本、分群效果和护栏，并观察扩量后单位成本是否下降。

### Stop Gate：什么时候应该停止

如果价值只能靠无法兑现的工时估算、人工监督长期不降、异常成本持续上升、归因无法成立或护栏不断恶化，就应该停项、收窄场景或退回 Copilot，而不是继续用“模型还会进步”解释。

## 结语：ROI 是结果契约，不是汇报数字

企业 AI 的 ROI 不是一个上线后才补的财务表格，而是项目设计的一部分。

它要求团队在开始前就回答：

- 业务结果是什么；
- 基线和反事实是什么；
- 哪些价值真正可以兑现；
- 哪些成本不能藏在别的部门；
- 谁承担失败和治理责任；
- 什么证据足以支持扩量；
- 什么条件出现时必须停止。

最终值得追求的不是“证明 AI 有用”，而是建立一套不会自欺的投资纪律：

> **用真实业务结果定义价值，用全口径成本检验经济性，用可信归因证明增量，用明确门槛决定扩张或停止。**
