RSI（Recursive Self-Improvement，递归式自我改进）正在从思想实验进入工程前沿：ICLR 2026 为它设立了专门 Workshop，口号是 "Design the loops, prove the gains"；OpenAI 公开招聘 RSI 方向的系统工程师和安全研究员；Anthropic 把“自动化 AI 研发”写进了 Responsible Scaling Policy 的能力阈值。

但这个词也在被迅速泛化。目前市场上至少有四类东西都被叫作 RSI：

1. 一次任务里的 Reflection、Critic、Retry；
2. 跨任务积累 Memory、经验或 Skill；
3. 自动优化 Prompt、Workflow、Harness 或模型权重；
4. Agent 修改自己的源代码，甚至修改“如何修改自己”的机制。

它们不是同一层。**有循环不等于递归，有优化不等于自我改进，benchmark 提升也不等于智能爆炸。**

这篇文章不做概念综述，只回答一个问题：

> **企业里的 Agent 系统，怎样才算真正在自我进化，以及怎样让这种进化安全地发生？**

## 一、先分级：从 Run 内修正到开放式 RSI

用一个五级框架可以把混乱的讨论拉直：

| 级别 | 机制 | 跨 Run 持久 | 改自身 | 企业判断 |
|---|---|:---:|:---:|---|
| R0 | Reflection、Retry、Replan | 否 | 否 | Runtime 基础能力，不是进化 |
| R1 | Memory、经验库、Playbook 增量 | 是 | 改上下文 | 可生产，须防错误记忆累积 |
| R2 | 证据门控的版本进化：Eval 驱动的 Prompt/Skill/Workflow/Policy Patch | 是 | 是 | **企业当前主目标** |
| R3 | 有限自指：Agent 修改自身 Harness/Code，独立验证后选代 | 是 | 含部分改进器 | 仅沙箱、低风险域探索 |
| R4 | 开放式 RSI：改进器、目标、评测器共同进化 | 是 | 全栈 | 尚无可安全部署的方案 |

研究界最可信的成果——Gödel Agent、SICA、Darwin Gödel Machine、AlphaEvolve——都是**有边界、有外部验证器的递归改进**，发生在固定任务或受控评测环境里。没有任何公开证据支持“把生产 Agent 放开让它自己改自己”。

所以企业的正确目标不是追逐 R4，而是把 R2 做扎实：

> **Agent 自动提出版本化的改进提案，由独立证据和发布门禁决定哪些提案成为下一代；目标、权限和门禁本身不允许 Agent 修改。**

## 二、自迭代的五个必要条件

很多团队以为“接上真实数据、让 Agent 定期复盘”就是自迭代。实际上一个完备的进化闭环需要五个条件，缺一不可。

### 条件 0：目标函数

优化什么？这是所有条件的上游。同一条信号，目标不同，归因结论可能完全相反——一次履约超时，对优化 P50 时效、P95 时效还是赔付率的系统，意味着三种不同的改进方向。没有明确目标函数，“这次结果好不好”本身无法判断。

### 条件 1：真实结果信号

信号是燃料，有四个质量维度：密度（样本够不够多）、质量（是真实结果还是噪声）、时效（反馈滞后多久）、覆盖（是否覆盖关键决策点）。

冷启动期信号稀疏，仿真可以批量产生训练信号，但仿真只能探索设计者能想到的策略空间，且必须持续用真实信号校正偏差。**仿真是补充，真实业务结果才是最终裁判。**

### 条件 2：归因机制

哪个决策导致了这个结果？一个最终结果往往经过多个决策节点，归因难度与决策链长度正相关：话术到转化只有三步，归因相对容易；一票货超时可能来自规划、选线、催单、承运商、清关任何一环，难度高一个量级。

实践建议由此而来：**优先在归因链最短的场景启动自迭代**，积累方法后再向复杂场景扩展。

### 条件 3：更新路径

怎么改？可更新的对象远不只 Prompt，按风险从低到高排列：

```text
Eval 用例补充
→ Context / Playbook
→ Skill 文档
→ Tool Schema 与低风险参数
→ Workflow 分支与阈值
→ 决策 Policy
→ Harness / 业务代码
→ 模型权重
```

判断原则：优先更新结构化、可版本化、可回滚的业务资产（Ontology、规则、Skill）；模型微调是最后手段——成本高、模型升级快，多数企业的投入产出比不成立。

### 条件 4：验证机制

改完是不是真的变好了？验证要分两层：宏观用 A/B 或准实验证明整体有效；微观用离线评测集防止某次迭代局部退化被整体数字掩盖。只有宏观验证是不够的。

### 条件 5：探索机制

信号→归因→更新→验证的闭环只能沿已知路径变好，发现不了更好的新路径。需要受控的小比例探索：用小流量跑新策略，产生新信号，再进入正常的归因验证流程。

## 三、真正的瓶颈是 Verifier，不是 Generator

当前所有证据都指向同一个结论：

> **Agent 会不会提出修改不是瓶颈；能不能独立证明修改有效，才是瓶颈。**

两个已被反复验证的教训：

**自我反思不可靠。**缺少外部信号时，LLM 的自我修正经常无效甚至降低准确率。同一个模型既当运动员又当裁判，会共享相同的盲点。企业里没有业务结果支撑的“Agent 自我复盘”，只是文本生成，不是学习。

**固定评测集会被做穿。**连续搜索 Prompt、Skill 或 Workflow 变体，会对验证集产生选择性过拟合——反复试到高分不代表能力提升。有研究显示，贪心接受修改的实验中出现了 30%—42% 的错误接受率，而带统计门控的接受规则能把它压到接近零。

所以验证体系至少需要：训练集、验证集与封存测试集分离；新鲜样本或时间切片 holdout；多指标护栏而不是单一成功率；最终用真实业务的 Canary 或 A/B 收口。

## 四、企业级架构：三个循环

把上面的条件组装起来，企业自迭代是三个不同时间尺度的循环：

```text
循环 A：Run 内快循环（秒—小时）
观察 → 规划 → 行动 → 核验 → 重规划或升级给人

循环 B：跨 Run 学习慢循环（天—周）
业务 Episode → 结果 → 归因 → 差距诊断
→ 版本化 Patch 提案 → Replay / 实验
→ 发布决策 → Canary → 监控 / 回滚

循环 C：改进机制的元循环（周—月）
审查归因是否可信、评测是否失真、实验是否有偏
→ 更新用例库、评测器、Patch 生成器和验收标准
→ 独立审批后发布下一版学习机制
```

真正的“递归”发生在循环 C：系统不只更新业务 Agent，也更新“以后如何发现、验证和选择更新”的机制本身。但正因如此，循环 C 必须有比业务 Agent 更高一层的独立治理——**不能让 Agent 通过降低验收门槛来证明自己变好了**。

同时有一批对象必须永远排除在自主修改之外：企业目标和 KPI 定义、法律合规边界、授权链和资金额度、关键人工审批、发布门禁和 Kill Switch、最终责任归属。这不是保守，而是防止系统通过“改考卷、改裁判、改目标”实现伪进步。

## 五、什么场景适合做第一个进化闭环

六条硬筛选标准：高频重复、结果可观测、动作可归因、动作可逆、边界可枚举、价值可计量。

按这个标准，客服工单分流、销售下一步行动、询盘—报价—打样这类场景适合度最高：Episode 清楚、反馈周期短、错误容易补偿。定价、授信、资金调度和战略决策则不适合作为第一个闭环——归因困难且失败代价高。

第一个 Pilot 最重要的验收指标，不是“自动发布了几个版本”，而是：

> **系统能否安全地拒绝一个证据不足或护栏变差的 Patch。**

能稳定说“不”的学习系统，才配说“是”。

## 六、结语

企业 Agent 的自我进化，不是让 Agent 无限制地改自己，也不等于 Prompt 自动优化或模型微调。它是一个工程闭环：

> **明确的目标函数，真实的业务结果信号，可信的归因，分层的更新路径，独立的实验验证，加上 Agent 无权触碰的发布门禁。**

拥有这个闭环的组织和没有的组织，差距会随时间复利拉大——因为前者的每一次运行都在为下一个版本积累证据，而后者的每一次运行只是消耗 Token。
