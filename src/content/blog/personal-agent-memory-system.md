长期使用个人 Agent 之后，一个微妙的问题会浮出来：

> 它不是完全不记得你，而是记得的方式越来越不够用。

一开始，记忆很简单。用户偏好、常用环境、少量长期事实直接写进系统记忆，每轮对话自动注入，Agent 自然显得“懂你”。

但当个人 Agent 开始承担长期工作，信息会迅速超过这个结构：健康档案、投资状态、工作主线、项目关系、机器环境、知识库、第二大脑、沟通偏好……它们都重要，却不应该以同一种方式进入每轮 Prompt。

如果全部塞进固定记忆，结果是：Agent 知道的背景更多了，但 Prompt 更胖、旧事实更容易污染判断、记忆容量很快爆掉。

我们最初试图用“分层记忆 + 按需检索”解决它。但真正改变方案的，是我追问了一句：

> **如果新记忆系统本身有缺陷，持续改写几个月以后导致 Agent 智能下降，怎么回滚？**

这篇文章记录的不是最终标准答案，而是一个记忆系统怎样在反驳中从“更懂我”转向“可追溯、可重建、可回滚”。

## 一、根矛盾：必到的太小，容量大的不到场

个人 Agent 的记忆大致可以拆成四层：

| 层级 | 典型载体 | 放什么 | 主要问题 |
|---|---|---|---|
| L0 | 固定 Memory / User Profile | 偏好、稳定身份、少量高频事实 | 每轮必到，但容量小 |
| L1 | Skill | SOP、工作流、经验教训 | 适合做法，不适合事实状态 |
| L2 | Session DB | 历史对话 | 完整，但需要主动检索 |
| L3 | Wiki / Projects / Files | 文档、档案、长期知识 | 容量大，但不会自动到场 |

根矛盾很清楚：

```text
L0：每轮必到，但太小。
L2/L3：容量很大，但不会自动到场。
```

所以第一版方案提出一个结构化知识层，专门存“当前事实”：按健康、项目、环境、人物等领域拆成卡片；每条事实带更新时间、来源、置信度和状态；当前问题命中某个领域时，再按需读取。

架构看起来很合理：

```text
用户消息
→ Topic Router
→ Memory Index
→ Candidate Memories
→ Reducer / Context Builder
→ 在预算内注入 Prompt
→ Agent 执行
```

它解决两个明显问题：不把所有背景塞进每轮 Prompt；同时让 Agent 知道去哪里找相关背景。

第一版还有一个正确判断：**记忆不是注入越多越好，而是检索越准越好。**

## 二、第一轮挑战：多层记忆如何持续更新

记忆分层以后，马上会遇到写入治理问题：谁来更新？什么情况下更新？旧事实怎么失效？

不能“每轮都记”。更合理的是事件触发：

| 触发事件 | 写入位置 |
|---|---|
| 用户明确说“记住”“以后都这样” | L0 或结构化事实层 |
| 长期事实发生变化 | 新事实写入，旧值标记 superseded |
| 长期主线结构变化 | L0 保存指针，详情进项目/Wiki |
| 复杂任务形成稳定流程 | Skill |
| 方法论沉淀 | Wiki / Blog |
| 临时任务进展 | 只留 Session DB |

所有事实还需要生命周期：

```text
last_updated / source / confidence
status: active | stale | superseded | archived
valid_from / expires_at
supersedes / superseded_by
```

此外可以定期做 Memory GC：发现过长的固定记忆、过期事实、缺失索引和高频新事实。但 GC 只能分风险运行：补索引、补时间戳可以自动；事实迁移应该先建议；删除、合并、覆盖用户事实必须确认。

到这里，方案已经像一个小型数据系统。但它仍然漏掉了最危险的问题。

## 三、致命问题：可变“事实库”会慢性污染

第一版潜意识里把结构化 YAML 当成事实源。如果系统会自动整理、覆盖、摘要和删除，几个月后可能发生：

- 不知道一条事实最早来自哪里；
- 不知道它是用户原话、Agent 推断，还是 Reducer 的摘要；
- 不知道哪次 GC 删除了关键细节；
- 不知道智能下降源于召回错误、摘要错误，还是事实源已被污染；
- 即使关闭自动加载，也恢复不了已经改坏的数据。

这类失败比“Agent 忘了”危险得多。它会让 Agent 看起来更懂背景，实际上更自信地错。

因此，Feature Flag 只能关闭新记忆注入，不能回滚已经发生的数据污染。真正的 Source of Truth 不能是一个持续被覆盖的“当前事实文件”。

第二版方案从这里换了底层原则：

> **当前知识视图可以变，原始记忆事件不能被悄悄改写。**

## 四、第二版：事件日志、当前视图、临时上下文

第二版把记忆拆成三个严格分离的层次：

```text
Raw Memory Event Log（不可变）
        ↓ build
Current Knowledge Views（可删除、可重建）
        ↓ retrieve + reduce
Prompt Memory Context（一次性派生物）
```

### 1. Raw Memory Event Log：不可变事实事件

用户提供新事实时，不覆盖旧文件，而是新增事件：

```json
{
  "event_id": "evt_001",
  "time": "2026-06-05T22:10:00+08:00",
  "actor": "user",
  "domain": "project",
  "type": "fact_asserted",
  "content": {"priority": "high"},
  "source": {
    "kind": "conversation",
    "session_id": "...",
    "quote": "这个项目现在是最高优先级"
  },
  "confidence": "high"
}
```

事实变化时也不改旧事件，而是增加 `fact_superseded` 事件，指向被替代的记录。

原则是：

```text
只追加，不覆盖；
只标记失效，不删除历史；
每条事实都能追到来源。
```

### 2. Current Knowledge Views：可重建当前视图

按领域生成的当前 Profile、项目状态卡等，只是从事件日志 Build 出来的视图。

它们可以被删除、重建和切换版本。如果视图生成逻辑有问题，就关闭当前视图、修复规则、从 Event Log 重新生成。

这和数据库的物化视图很像：

- Event Log 是真相；
- Knowledge View 是缓存和索引；
- Prompt Context 是当前查询的一次性结果。

### 3. Prompt Memory Context：一次性派生物

每轮真正进入 Prompt 的只是 Reducer 生成的小摘要。它必须带时间和来源，不确定时保留冲突，不能把摘要反向写回事实层。

这个单向数据流非常重要：**Prompt 为回答服务，不应该拥有改写长期事实的权力。**

## 五、真正的回滚有两层

“可回滚”至少包含两件不同的事。

### 1. 回滚注入策略

如果自动召回导致回答变差，可以关闭 Autoload，让 Agent 回到固定 L0 + 手工 Search / Read / Session Search 的模式。

这解决的是：新记忆进入 Prompt 后导致智能下降。

### 2. 回滚数据状态

如果视图、迁移或 GC 已经写坏数据，仅关闭 Autoload 不够。还需要：

```text
append-only event log
+ 定期 snapshot
+ 版本化变更和 diff
+ 按 domain 恢复
```

每次自动迁移、Schema 变化和批量 GC 前，都应该保留快照和变更记录。回滚不能靠“凭印象删文件”，而应该能明确恢复到某个版本或从不可变日志重新 Build。

## 六、Shadow Mode：先观察，不影响回答

第二版最重要的安全机制不是更复杂的检索器，而是 Shadow Mode：

```text
用户问问题
→ Router 判断候选领域
→ Retriever 召回记忆
→ Reducer 生成候选上下文
→ 只记录日志，不进入 Prompt
→ 人工抽查
```

先观察几周，重点检查：

- 是否召回错误领域；
- 是否把旧事实当成当前事实；
- 是否把冲突事实揉成确定结论；
- 是否注入过量；
- 高风险领域是否缺少时间和来源；
- 回答是否变得“更懂背景但更自以为是”。

通过后再按风险灰度：先环境和项目，再工作与第二大脑，最后才是健康和投资。不同领域错误代价不同，不能用同一个自动化等级。

## 七、停止线：什么时候立刻关掉

一旦发生以下情况，应该关闭自动加载，只保留 L0 和手工检索：

1. 用户指出 Agent 引用了旧事实或错事实；
2. 单轮记忆注入连续超过预算；
3. 高风险事实没有时间和来源；
4. Reducer 把冲突事实压成一个确定结论；
5. 用户感觉回答“更懂背景，但更自以为是”。

最后一条尤其重要。记忆系统最危险的失败，不是 Agent 说“我不知道”，而是它自信地说“我知道你”。

## 八、一个安全 MVP

如果在现有个人 Agent 上实验，不应该一开始就替换核心 Memory。最小路径是：

```text
1. 建独立 memory-lab 沙盒
2. 复制少量现有记忆，不移动原始数据
3. 手工创建几张 Knowledge Card
4. 写 append-only Event Log
5. 从日志生成 Current Views
6. Shadow Mode 只记录候选注入
7. 人工评估召回、摘要和冲突处理
8. 只对低风险领域灰度启用
9. 稳定后再讨论高风险领域
```

MVP 只验证三件事：

- **召回是否准确**：该出现的出现，不该出现的不出现；
- **摘要是否克制**：进入 Prompt 的内容少而准；
- **回滚是否真实**：错误写入、错误视图和错误注入都能定位撤销。

如果这三件事做不到，宁可不实施。一个不可靠的长期记忆系统，可能比没有长期记忆更危险。

## 结语

个人 Agent 的记忆不是为了显得贴心，而是为了在长期合作中减少重复沟通、保持事实一致、尊重时间变化，并在不确定时知道自己不确定。

它至少要同时满足四个目标：

1. **连续性**：长期主线和重要事实不丢；
2. **时效性**：旧事实会失效，不永久污染判断；
3. **经济性**：按需、预算内注入，不让 Prompt 膨胀；
4. **可逆性**：系统试错不会污染到无法恢复。

因此，好的个人 Agent 记忆系统不是一个“记忆功能”，而是一套运行机制：

```text
个人数据层
+ Append-only 事实事件日志
+ 可重建当前视图
+ 检索器与 Prompt Reducer
+ 生命周期治理
+ Shadow Mode
+ 发布与回滚
```

一句话总结：

> **没有 Append-only Event Log 的多层记忆系统，不是可进化系统，而是慢性污染系统。**
