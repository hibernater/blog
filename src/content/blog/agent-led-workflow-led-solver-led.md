企业开始建设 AI 系统时，一个常见路径是：先选定一个 Agent Framework，再往业务里找场景。

这个顺序几乎注定会出问题。不是因为框架不好，而是因为它把“谁来主控这个问题”当成了默认答案——所有问题都交给 LLM Agent 来规划、决策和推进。

我的判断是：

> **主控权应该由问题结构决定，而不是由技术潮流决定。LLM Agent、工作流引擎和专业求解器各自擅长的问题类型不同，混淆主控会同时损失可靠性和智能。**

## 一、为什么“先选框架，再找场景”会失败

功能表会骗人。LangGraph、Temporal、CrewAI、AgentScope 都能勾上“支持持久化、支持多 Agent、支持工具调用、支持人工审批”，但它们管理的核心问题完全不同。

“都能实现”不等于“解决同一个问题”。只有回到具体业务场景，才能看清：

- 哪种状态是权威状态；
- 哪种失败最昂贵；
- 哪个对象必须成为系统的一等公民；
- 框架的可靠性承诺到底落在哪一层。

先选框架的团队通常会走向一个更糟的结局：为每个研究过的框架都在业务里找一个位置，最后叠加多套 Runtime、多套状态、多套 Trace、多套重试和权限。框架应该用于解决问题，而不是制造问题。

## 二、判断主控权的五个诊断问题

面对一个具体场景，先不谈技术名词，问五个问题：

### 1. 权威状态在哪里

订单、支付、库存、合同的现实状态存在业务系统里；Agent 的假设、证据和计划存在它自己的上下文里。两者冲突时听谁的？

如果权威状态在外部业务系统，而系统主要工作是按既定规则推进状态变化，那么主控者更应该是工作流，而不是每一步都重新“思考”的 Agent。

### 2. 失败代价有多高

错一次、漏一次、重复一次分别有什么后果？重复扣款和重复发一封提醒邮件是完全不同的问题。失败代价越高，越需要确定性执行、幂等和补偿机制，越不能依赖概率性规划。

### 3. 动作边界是否可枚举

如果一个场景的所有合法动作可以列成清单、每个动作的前置条件和审批边界都清楚，那么把动作选择交给规则或策略表往往更稳。动作空间开放、需要理解非结构化输入并动态组合的场景，才是 Agent 的主场。

### 4. 时间跨度有多长

秒级完成的问答和跨天等待供应商回复、人工审批的任务，需要的是两种系统。时间跨度越长，持久状态、恢复和超时处理越重要——这些是工作流引擎数十年积累的能力，不是 Loop 加长上下文能替代的。

### 5. 有没有更简单的反事实基线

在引入任何框架之前，先问：一次结构化 LLM 调用、一张数据库状态表、一个定时任务加消息队列，能不能可靠解决这个问题？只有当最简单方案出现明确缺口时，更重的架构才有必要。

## 三、三种主控模式

用这五个问题过滤后，大多数企业场景会落进三种主控模式之一。

### Agent-led：探索式问题

输入非结构化、路径无法预先枚举、需要在执行中动态判断下一步。例如：从多个信息源调查一个客户投诉的根因；理解一份复杂需求并起草方案；跨系统排查一个异常。

这类问题的特征是**路径本身是产出的一部分**。适合让 LLM Agent 主控：观察、规划、行动、再规划。Workflow 和工具在这里是 Agent 的手脚。

### Workflow-led：过程确定性问题

路径可枚举、状态转换明确、失败必须可恢复、动作不可重复执行。例如：订单履约、审批流、对账、赔付处理。

这类问题的核心资产是**状态机和事务语义**。应该让工作流引擎主控：Event History、Timer、Signal、重试、补偿。LLM 在其中作为节点被调用——处理非结构化输入、生成候选判断——但不主控流程推进。

把这类问题交给 Agent 主控的典型症状是：系统跑通了 Demo，但无法回答“上周三那笔卡在中间的任务现在处于什么状态、怎么恢复”。

### Solver-led：最优化问题

目标函数明确、约束可形式化、解空间巨大。例如：排产、路径规划、库存配置、资源分配、定价。

这类问题已有预测模型、因果推断、运筹求解器等专业方法，几十年的数学积累不会被一个通用语言模型替代。LLM 在这里的正确角色是**翻译层和解释层**：把业务语言翻译成求解器的输入，把求解结果解释给人。

让 LLM 直接“想”一个排产方案，本质上是用概率文本生成冒充约束求解——偶尔看起来合理，无法保证可行性和最优性。

## 四、混合系统：唯一主控，按需调用

真实企业场景往往是混合的。一条采购链路里，需求理解是探索式的，审批和下单是过程确定性的，供应商选择可能是最优化的。

混合不等于混乱。原则是：

> **每个闭环选择唯一主控，其他能力作为被调用方接入；默认一个主运行时，能不用第二套就不用。**

例如采购 Agent 的一种合理分工：

```text
Agent-led：需求理解、比价分析、异常调查
Workflow-led：审批、预算控制、ERP 下单、付款、交付跟踪
Solver-led：批量采购的量价优化（如果规模值得）
```

Agent 负责理解和判断，把结论交给工作流；工作流在需要判断的节点调用 Agent；求解器在明确的优化点被调用。三者边界清楚，责任才能清楚。

反过来，最常见的两种错位是：

- **让 Agent 冒充工作流引擎**：用 Prompt 里的步骤描述代替持久状态机，跨天任务一旦中断就无法恢复；
- **让工作流冒充 Agent**：把本质上需要动态探索的问题硬编码成几十个分支，每遇到新情况就加一个 if。

## 五、这不是给 Agent 降级

有人会把这套判断读成“Agent 只配做小事”。恰恰相反。

让 Agent 去干工作流引擎和求解器的活，才是真正的降级——它会在自己最不擅长的确定性执行和数学优化上暴露短板，然后整个“企业 AI”项目被贴上不可靠的标签。

把主控权还给问题结构，Agent 才能集中在它真正不可替代的地方：理解非结构化世界、在开放空间里探索、把模糊的业务语言翻译成可执行的判断。

选型的最终原则仍然是那句话：

> **先用业务场景搞清楚要解决的问题，再决定谁来主控；框架用于解释问题，不用于制造问题。**
