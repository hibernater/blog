判断一个企业 AI 系统，经常会落入几个很容易量化、却不太重要的问题：用了多少模型，有多少 Agent，接了多少工具，能生成多少 Workflow，界面像不像一个“企业大脑”。

这些都不能回答最关键的问题：

> **这个系统是在帮助人理解和建议，还是已经能够进入真实业务运行，并根据结果持续改进？**

我曾经用五个标准判断“业务助理”和“业务操作系统”的区别。继续讨论和实践后，我发现 Knowledge、Action、Harness 与 Governance 被压在几个抽象词里，很容易绕，于是把它修正为六个基本要素：

```text
1. Ontology：懂业务对象
2. Knowledge & Action：懂业务规律，也知道能做什么
3. Goal & Metrics：知道优化什么、什么叫好坏
4. Execution Harness：能把动作跑成真实任务
5. Feedback & Learning：知道结果，并让下一轮变好
6. Governance：知道边界、风险、权限和冲突处理
```

它们不是行业标准，也不是要求企业第一天就建齐的产品模块，而是我用来检查一个系统有没有漏掉关键责任的判断框架。

## 一、模型、知识库和工具加起来，仍然不一定是业务系统

一个系统可以非常聪明：

- 读完公司所有文档；
- 回答业务问题；
- 生成分析、计划和话术；
- 调用几个 API；
- 记住部分历史对话。

但如果它不知道正在处理哪个客户、订单或项目，不知道当前目标和约束，不知道动作是否真的发生，也不知道结果是否改善，它仍然只是一个能力很强的助理。

业务操作系统比业务助理多的，不是“更会说”，而是两件事：

```text
能把判断变成受治理的真实业务运行
+ 能根据真实结果持续修正下一轮
```

六要素就是对这两件事的展开。

## 二、六个要素分别回答什么问题

### 1. Ontology：业务世界里到底有什么

Ontology 回答：

- 业务实体有哪些；
- 实体之间是什么关系；
- 实体处于什么状态；
- 哪些事件会改变状态；
- 状态变化在业务上意味着什么。

客户、线索、商品、订单、合同、供应商、物流节点、责任人，不能只是一段文字里的名词。系统要能区分对象，识别它们的关系和版本，并知道一次动作预期改变哪个状态。

没有这一层，AI 可以解释材料，却无法稳定操作业务世界。它今天把“客户”理解为购买主体，明天又把渠道商和联系人混在一起，每次都能讲通，但口径不会稳定。

### 2. Knowledge & Action：不仅懂规律，还知道能做什么

Knowledge 不是把文档塞进向量库。真正可操作的 Knowledge 要回答：

- 什么状态代表机会、风险或异常；
- 哪些业务规则和经验适用于当前对象；
- 在这种状态下有哪些候选动作；
- 动作可以调度哪个系统、流程、角色或资源；
- 动作的前置条件、成本与副作用是什么。

例如，识别到“订单可能延期”只是理解；知道可以补料、换供、调整排产、修改承诺、升级负责人，并知道每个动作的权限和代价，才进入 Action。

因此我把 Knowledge 与 Action 放在同一个要素里：**不能指导行动的知识，无法独立构成业务运行能力。**

### 3. Goal & Metrics：系统到底在优化什么

系统即使理解对象、拥有动作，也必须知道：

- 当前业务目标是什么；
- 主结果指标是什么；
- 哪些过程指标可以提前预警；
- 哪些护栏不能被伤害；
- 多个目标冲突时优先级如何决定；
- 结果应该在多长时间窗口内观察。

只给一个 KPI 往往不够。销售 Agent 只优化成交额，可能透支退款率、投诉、触达频次或长期客户关系。真正可运行的目标应是一份结果契约：主结果、护栏、风险、成本、时间窗口和归因口径一起出现。

### 4. Execution Harness：把判断跑进真实世界

Execution Harness 回答：

- 发现问题后如何发起任务；
- 谁负责，AI、系统和人怎样分工；
- 需要调用哪些工具和 Workflow；
- 哪些动作自动执行，哪些需要审批；
- 超时、失败、重试和补偿怎么处理；
- 什么算完成，怎样验收和回写。

这是业务助理与业务操作系统的重要分水岭。助理可以给建议；操作系统必须让动作进入真实系统，留下可追踪状态，并处理运行中的异常。

一次 Tool Call 返回 success，并不代表订单、客户或库存真的发生了预期变化。关键动作后还需要回读业务事实源，核对状态，必要时重试、补偿或升级给人。

### 5. Feedback & Learning：结果怎样改变下一轮

反馈不是记录“用户点了赞还是踩”，而是回答：

- 动作有没有发生；
- 对象状态是否改变；
- 业务指标是否改善；
- 变化是不是由这次动作导致；
- 错误来自知识、状态、策略、工具、流程还是权限；
- 应该更新哪一种业务资产；
- 更新后如何验证、灰度和回滚。

系统可以更新的远不只是模型参数，也包括 Ontology、Knowledge、Action 条件、Skill、Workflow、Harness、审批边界和 Eval 集。

对大多数业务团队，优先更新这些可解释、可版本化、可回滚的业务资产，通常比模型微调更现实。

### 6. Governance：什么能做，什么不能做

Governance 回答：

- 哪些动作可以自动执行；
- 哪些只能在 Shadow Mode 运行；
- 哪些必须人工审批；
- 哪些动作禁止进入系统；
- 预算、频次和资源上限是什么；
- 多个局部目标冲突时听谁的；
- 高风险动作如何审计、回滚和追责。

Governance 不是系统跑完以后再检查，而是贯穿全链路。它既过滤候选动作，也是 Runtime、工具、数据和组织责任的边界。

而且治理不能只写在 Prompt 里。金额上限、越权访问、禁止工具和跨租户数据边界，必须由模型外部的身份、策略、沙箱、审批和执行系统强制。

## 三、六要素不是并列清单，而是一条运行闭环

六要素更接近这样的运行顺序：

```text
Goal & Metrics
决定要优化什么
        ↓
Ontology + Knowledge & Action
理解对象、状态和规则，生成候选动作
        ↓
Governance
筛选、授权，决定能不能做和怎样做
        ↓
Execution Harness
把动作变成真实任务并运行
        ↓
Feedback & Learning
观察结果、归因、验证并形成版本化更新
        ↺
回写目标、对象、知识、动作、治理和 Harness
```

可以把中间两步压成两个公式：

```text
Candidate Action
= Goal & Metrics
+ Ontology / Knowledge / Action

Executable Action
= Candidate Action
+ Governance Check
```

这也解释了为什么只增加模型能力不能自动补齐企业 AI。模型可以参与每一步，但每一步都有模型之外的事实、权责和运行机制。

## 四、Memory 为什么不是第七个要素

Memory 很重要，但它和六要素不在同一个维度。

六要素回答的是：

> 一个系统要从助理进入业务运行，必须承担哪些业务责任？

Memory、Context、Trace、Eval、Tool、Permission、Versioning 回答的是：

> Agent 如何连续、稳定、可追溯地承载这些责任？

Memory 可以保存对象定义、指标口径、运行状态、审批记录和学习补丁，但“记住订单”不等于知道订单的正式业务状态；“记住用户偏好”也不等于拥有修改业务对象的权限。

因此更准确的分层是：

```text
业务能力层：六要素
        ↑
Agent 基础设施层：
Memory / Context / Trace / Eval / Tool
Permission / Versioning / Patch Store
```

把 Memory 列成第七个业务要素，会把“业务责任缺失”和“Agent 承载不可靠”混成一个问题。

## 五、六要素不是二元门槛，而是成熟度模型

不能说“没有六要素就什么都不是”。一个优秀的业务助理并不需要自己执行全部动作，但至少要有轻量 Ontology、Knowledge、Goal Context 和不确定性边界。

可以用下面的分层做诊断：

| 层级 | 形态 | 主要能力 |
|---|---|---|
| L0 | 聊天机器人 | 主要依靠语言生成，没有稳定业务模型 |
| L1 | 业务问答助手 | 轻量 Ontology + Knowledge |
| L2 | 合格业务助理 | 加上 Goal Context 与不确定性边界，判断稳定、有依据 |
| L3 | 经营参谋 | 能围绕目标和指标提出较稳定建议，但不负责执行 |
| L4 | 业务 Agent / Workflow 系统 | 加上 Execution Harness，能发起和推进真实任务 |
| L5 | 业务操作系统 | 六要素形成完整闭环，能运行、反馈、学习并受治理 |

这不是一条所有企业都必须走到 L5 的升级路线。很多场景停在 L2 或 L4 就已经有真实价值。关键是不要把一个回答更顺、接了更多工具的助理，包装成已经能够运行企业业务的操作系统。

## 结语：六个问题，比“有多少 Agent”更有用

以后判断一个企业 AI 系统，我更愿意问六个问题：

1. 它操作哪些业务对象，对象、关系和状态稳定吗？
2. 它知道业务规律，以及在不同状态下可以做什么吗？
3. 它知道当前目标、好坏标准和护栏吗？
4. 它能把判断变成真实任务，并处理失败和异常吗？
5. 它能看到结果、合理归因，并让下一版本变好吗？
6. 它知道哪些能自动、哪些要人审、哪些绝不能碰吗？

这六个问题都能回答，系统才开始接近业务操作系统。

但最重要的不是名字，而是：**它是否让真实业务在清晰目标、可验证状态和受治理行动之间持续运转。**
