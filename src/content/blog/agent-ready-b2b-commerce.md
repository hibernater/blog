未来一部分购买行为可能不再从“人打开商城”开始，而是从一句自然语言需求开始：

> 帮我找一批符合某项认证、能在三周内交付、支持小批量定制的供应商，比较价格和履约风险，给出采购建议。

如果执行这件事的是 AI Agent，传统电商平台的很多默认前提都会变化。详情页是给人看的，Agent 更需要结构化事实；搜索排序是给人浏览的，Agent 更需要可比较的供应能力；“加入购物车”是人的动作，Agent 还需要身份、授权和预算边界。

这带来一个值得提前讨论的问题：

> **当购买者从人变成 Agent，B2B 平台究竟要把什么准备好？**

我的判断是：B2B 的 Agent-ready 不是给网站加一个 AI 导购，而是把供给、交易和履约改造成一套机器可理解、可调用、可授权、可验证的行动环境。

## 一、外部信号：电商栈正在重新面向 Agent 编排

[2025 年 7 月，BigCommerce Holdings 发布新的母品牌 Commerce](https://www.commerce.com/press/commerce-launch-press-release-2025/)，将 BigCommerce、Feedonomics 和 Makeswift 放进同一个“agentic commerce”叙事。官方材料至少表达了一个方向：即使消费者或采购者不再访问商家网站，平台仍希望掌握商品事实、订单执行和商家关系。

其中最容易被低估的不是结账，而是商品数据层。传统 Product Feed 主要服务搜索、广告和 Marketplace，常见字段是标题、类目、图片、价格和库存；Agent 做购买判断时，需要更多：规格兼容性、价格适用条件、交期、认证、替代品关系、退换规则、事实来源和更新时间。

但这里必须降温：一组产品发布放在同一战略叙事下，不等于已经形成完整的 Agent Commerce 协议，更不等于复杂 B2B 采购已经端到端跑通。它只是一个清晰的外部信号：**电商基础设施正在从 Human-facing 向 Agent-facing 增加一层接口。**

## 二、B2C 的 Agent 结账，不等于 B2B 的 Agent 采购

B2C 的标准购买链相对短：

```text
找商品 → 比价 → 确认库存 → 用户授权 → 支付 → 下单
```

B2B 往往是：

```text
理解采购需求 → 补全规格 → 校验供应商准入
→ 获取客户专属价格 → 比较 MOQ、交期、账期
→ 询价或谈判 → 生成 PO → 预算/法务/采购审批
→ 下单或签合同 → 收货、验收、开票、付款
```

这两条链路不是复杂度多几步的区别，而是对象体系不同。B2B Agent 至少需要五类核心对象：

1. **Buyer Organization**：哪个公司、哪个部门、成本中心、采购政策和审批链；
2. **Transaction Authority**：谁授权 Agent、能采购什么、金额上限、是否必须比价；
3. **Commercial Agreement**：合同价格、阶梯价、账期、返点、区域和有效期；
4. **Supply Commitment**：数量、交期、质量、认证和赔付责任；
5. **Evidence & Outcome**：为什么选它、比较过什么、谁批准、实际交付是否符合承诺。

没有这些，Agent 最多是一个更聪明的商品搜索器，还不是企业采购执行者。

## 三、从 Product Catalog 到 Supply Capability

对标准零售品，商品目录可以覆盖相当一部分事实；对产业 B2B，“现在卖什么”远远不等于“实际能做什么”。

一个工厂目录里没有某个 SKU，不代表它不能改规格、改材质、联合打样或小单快反；反过来，目录里写着“七天发货”，也不代表它此刻真的有产能兑现。

因此 B2B 真正需要从：

```text
Agent-ready Product Catalog
```

升级为：

```text
Agent-ready Supply Capability Network
```

两者的区别是：

| 商品目录 | 供应能力网络 |
|---|---|
| 现在卖什么 | 实际能解决什么需求 |
| SKU 属性 | 工艺、设备、产能与柔性 |
| 标准价格 | 数量、规格、交期共同决定的报价 |
| 当前库存 | 可承诺产能 |
| 商品评价 | 真实履约能力 |
| 点击、成交 | 打样、交付、质量、复购结果 |

供应能力不是静态资料，而是带条件、带时间、带证据、带历史结果的承诺。

## 四、Agent-ready B2B 的六层基础设施

如果把这个判断落成架构，至少需要六层：

### 1. 需求语义层

把一句模糊需求编译成结构化采购任务：用途、规格、数量、预算、交期、认证、可替代条件和风险偏好。

### 2. 供应能力层

不是只有商品属性，还包括工艺、设备、产能、柔性、认证、历史履约和可组合能力。每项事实要有来源、更新时间和可信度。

### 3. 交易行动层

Agent 可调用的不只是搜索 API，还包括询价、报价、打样、锁产能、签合同、支付、跟踪履约、验收和售后等 Action。

### 4. 身份与授权层

明确 Agent 代表谁、能花多少钱、能否自主下单、哪些类目受限、什么动作必须多人审批。支付只是其中一部分，不能代替完整采购治理。

### 5. 承诺与履约层

报价不是终点。交期、质量、数量、服务和赔付需要形成可追踪的 Commitment；实际结果反过来更新供应商能力和可信度。

### 6. 证据与治理层

记录 Agent 基于什么事实做出选择，调用了什么动作，谁批准，最终结果如何。高风险动作必须审批，可补偿动作要有补偿路径，不可逆动作要显式标注残余风险。

六层连起来，外部 Agent 调用的就不再是一个商品搜索 API，而是一套受治理的采购执行接口。

## 五、谁会拥有 Agent Commerce 的控制权

Agent Commerce 不会只有一个赢家。至少四类玩家在争夺不同控制点：

- AI 入口控制用户意图和购买决策；
- 电商平台控制商品、订单和商家系统；
- 支付网络控制身份、授权和资金；
- Marketplace 控制发现、信任与交易闭环。

平台面临一个结构性矛盾：既要让外部 Agent 容易发现和成交，又不能因此失去客户关系、价格控制和商家治理。如果只开放商品数据，平台可能退化成低毛利后台；如果不开放，又可能错失新的 Agent 流量入口。

真正的壁垒不会是“接入了多少个 AI 助手”，而是三件事：

1. 谁拥有可验证、持续更新的供给事实；
2. 谁能提供受授权、可执行的交易 Action；
3. 谁掌握从承诺到履约结果的闭环数据。

## 六、协议会统一接口，但不会替平台完成业务语义

支付和 Agent 互操作协议正在快速出现，它们会解决一部分共性问题：Agent 如何发现能力、如何传递授权、如何发起结账、如何在不同系统间交换交易信息。

但协议不会替一个 B2B 平台回答：什么叫合格供应商？某种工艺能力如何证明？交期承诺如何计算？打样失败如何归责？这些仍然需要行业 Ontology、行动契约、治理规则和真实履约数据。

因此，协议层越成熟，平台真正的差异化反而越向业务语义下沉。

## 结语

Agent-ready B2B 的终局不是“让 Agent 能买到商品”，而是：

> **让 Agent 能在明确授权下，理解需求、识别真实供应能力、形成带条件的交易承诺，并用履约结果持续校准下一次采购。**

目前这仍是一个方向判断，不是已完成的行业事实。但如果购买入口真的逐步 Agent 化，B2B 平台今天就该开始准备的，不是聊天界面，而是供给语义、交易行动、授权治理和结果证据。
